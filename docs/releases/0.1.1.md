# RAGLeakGuard 0.1.1 corrective release notes

**Status:** proposed corrective version; not published, tagged, or released.

These are the canonical notes for candidate `0.1.1`. They describe the proposed reviewed artifacts,
not the currently published PyPI package. Publication requires a later explicit human approval of
the exact commit and exact artifact hashes. PyPI Trusted Publishing is not configured by WP8.

## Security correction

PyPI `0.1.0` contains an unsafe direct Chroma path and **must not be used for Chroma scanning**.
ChromaDB 1.5.0 and 1.5.9 exhibited durable store mutation during client construction or reads.
[Issue #15](https://github.com/Agenvana/RAGLeakGuard/issues/15) was deferred as `not planned`; it
was not completed.

The proposed `0.1.1` artifacts contain the current fail-closed direct/live boundary. Direct/live
Chroma scanning and monitor new scans remain disabled. The only activated Chroma route consumes a
complete, quiescent/full-filesystem snapshot created separately by the operator and returns bounded
aggregates after copy confinement, two-pass equality, detection, worker termination, revalidation,
cleanup, and atomic report finalization.

The operator—not RAGLeakGuard—must create the snapshot. RAGLeakGuard does not prove its provenance,
quiescence, completeness, or transactional atomic consistency. Detection is best-effort and a clean
result is not proof of safety, compliance, or absence of sensitive data.

## Compatibility and upgrade guidance

- Python 3.13+ does not match `0.1.1` because its package metadata requires
  `>=3.9,<3.13`; the unsafe `0.1.0` metadata may still match Python 3.13+ until that
  release is yanked. Users on Python 3.13+ must not assume
  `pip install -U ragleakguard` installed the corrective version. They must verify the installed
  version, for example with `python -m pip show ragleakguard` and
  `python -c "import ragleakguard; print(ragleakguard.__version__)"`, and require exactly
  `0.1.1` before relying on the correction. There is no supported corrective Chroma path on
  Python 3.13+.
- The old `chroma` extra was replaced by `chroma-snapshot`. Using the old extra does not install
  the required exact ChromaDB 1.5.9 dependency. On one of the five supported activation cells, use
  `python -m pip install "ragleakguard[chroma-snapshot,detect]==0.1.1"` and verify the installed
  RAGLeakGuard and ChromaDB versions.
- Legacy `--path` is rejected. The bounded operator-snapshot invocation requires
  `--snapshot`, `--work-parent`, `--source-id`,
  `--acknowledge-offline-complete-snapshot`, and `--report`:

  ```bash
  ragleakguard scan --source chroma \
    --snapshot /private/offline-snapshot \
    --work-parent /private/ragleakguard-work \
    --source-id source-1 \
    --acknowledge-offline-complete-snapshot \
    --report /private/reports/source-1.md
  ```

- CLI options, exit meanings, detection policy, connector behavior, monitor behavior, report format,
  risk policy, and persisted monitor-state schemas are unchanged by WP8.
- `ragleakguard.__version__`, wheel/sdist metadata, release notes, and a future exact `v0.1.1` tag
  must all equal `0.1.1`; Hatch reads the runtime value as the single version source.
- Do not treat a source checkout or an unreviewed CI artifact as a published release. A future
  maintainer-approved installation must use the reviewed artifact hashes from the candidate evidence.
- Do not reuse or replace files for an existing package version. PyPI `0.1.0` remains published and
  has not been yanked by WP8.

## Release-system status

WP8 adds a non-publishing build-once candidate workflow and a separate dormant manual publication
workflow. The candidate workflow has no publication credential, secret, or `id-token` permission.
The publication workflow never rebuilds and cannot reach its PyPI job unless the exact tag, commit,
version, artifact hashes, candidate evidence, protected `pypi` environment, and external PyPI OIDC
Trusted Publisher are all present. WP8 does not create the tag, release, environment protection, or
external trust relationship and does not publish to PyPI or TestPyPI.
